Job Portal Chatbot Copilot with Filter Integration
Conversational Job Filter Chatbot – Implementation Guide
This guide outlines a phased plan to implement a conversational “copilot” chatbot for a job portal that dynamically filters and displays job listings based on natural language input. The solution will replace or complement the existing filter UI (for keywords, location, company, job type) and use an LLM (GPT-4) to interpret user queries (e.g. “Show me remote React jobs in Tel Aviv”) into structured filters. We emphasize industry best practices at each phase to ensure the final product is production-ready, accessible, and robust.
1. Requirements Gathering and Scoping
Detailed Steps:
1. Stakeholder & Goal Identification: Engage product owners, job seekers (end-users), and engineers to clarify project goals. For example, the primary goal might be to improve the job search UX by allowing conversational filtering (instead of form-based filters), thus increasing user engagement and successful job matches.

2. Use Case Elicitation: Gather specific user scenarios and requirements. Document user stories such as: “As a job seeker, I want to ask for jobs using natural language so I can find relevant positions without manually using filters.” List queries the chatbot should handle (job title/skills, location, remote vs on-site, company names, etc.). Include multi-criteria queries (e.g. “remote React developer jobs in Tel Aviv at Google”), single-criterion queries, and follow-ups (like “only the remote ones”).

3. Scope Definition: Clearly define in-scope functionality (e.g. filtering and refining job listings via chat, answering basic questions about the job listings) versus out-of-scope (e.g. applying to jobs, answering HR policy questions, general chit-chat beyond the job search domain). Decide whether the bot will handle small talk or strictly job queries (likely keep it focused). Identify any compliance requirements (privacy of user input, storing chat logs, etc.).

4. Non-Functional Requirements: Document performance and quality criteria. For example, specify target response time (the chatbot should filter jobs within e.g. 2 seconds of user query), accuracy (the bot should correctly interpret at least e.g. 90% of typical queries), and availability. Include constraints like supported languages (if multilingual), and how the system will handle peak usage or API rate limits.

5. Success Metrics: Establish how to measure success post-launch (e.g. increased job search conversion, reduction in manual filtering actions, user satisfaction ratings for the chatbot). These will guide testing and evaluation later. Ensure these metrics are agreed upon and feasible to track.

2. Conversational UX and NLP Intent Mapping
Detailed Steps:
               1. Define Conversational Flow: Design how a typical dialogue will progress. This includes the greeting (e.g. chatbot says “Hello, I can help you find jobs. What are you looking for?”), how the bot presents results (text summary plus updating the job list UI), and how users can refine or ask follow-ups. Map out a few example dialogues to cover scenarios: a direct one-shot query vs. a step-by-step narrowing (user: “I need React jobs.” bot: “Sure. Any preferred location?” user: “Tel Aviv.”). Ensure the flow feels natural and efficient compared to using filters manually.

               2. Intent & Entity Mapping: Determine how user inputs will be understood. The primary intent here is likely “SearchJobs” (user wants to find jobs) with entities/slots like skill/role, location, company, job_type, etc. For example, “remote React jobs in Tel Aviv at Google” -> intent: SearchJobs, entities: skill=React, location=Tel Aviv, company=Google, job_type=remote. List synonyms or variations: e.g. “remote” vs “work from home”, city name variations, common role titles. Decide if the bot will handle other intents like greetings, thanks, or out-of-domain questions – typically, a minimal implementation handles a greeting and a fallback for off-topic questions (e.g., “Sorry, I can only assist with job searches.”).

               3. NLP Approach: Choose between a rules-based entity extractor, a traditional NLU (like Rasa), or using the LLM directly. Best practice: Leverage GPT-4’s strong NLP capabilities instead of building a custom intent classifier from scratch. Specifically, plan to use OpenAI’s Function Calling feature or a prompt-based parsing: define a function like search_jobs(filters) with parameters (location, keywords, etc.), and let GPT-4 pick out those parameters from the user’s requestelastic.co. This way, the model itself maps the conversational input to structured data, acting as the intent mapper. Prepare a schema for these parameters and example values for clarity.

               4. Dialogue Management: Consider how the chatbot will manage context over multiple turns. For instance, if a user asks a follow-up like “Show me the first one” or “Only remote ones now,” the system must recall the context of previous results or query. Plan to use short-term memory: maintain the last query and results in the session state. Using an LLM, you might include the conversation history in prompts or use an external memory store. For now, define rules like: if the user’s new query is incomplete (e.g. just says “in Tel Aviv” after a prior query), the bot should combine it with the previous filters. This ensures continuity. Designing how to detect and handle context-dependent queries is crucial for a smooth UX (e.g., “the second one” referring to a previously listed job requires short-term memorymedium.com).

               5. Clarification and Fallback UX: Decide how the bot will handle ambiguity or unknowns. If a user query is missing important info (like just “Show me jobs” – too broad), determine if the bot should: (a) ask a clarifying question (“Sure – any particular location or technology?”), (b) show a generic list of latest jobs (with a prompt that the user can refine), or (c) do both. Also design polite fallback messages for queries outside the bot’s knowledge (user asks about quantum physics, etc.) – e.g., “I’m sorry, I can only help with finding jobs at the moment.” Plan a tiered approach: a generic apology and guidance on first failure, perhaps a rephrase or options on second, and a final fallback like offering human support or a FAQ link on persistent confusiontencentcloud.comtencentcloud.com. Keeping the tone friendly and helpful even in error cases is a UX best practice.

3. Backend API Enhancement (Search/Filtering via Structured Params)
Detailed Steps:
                              1. Assess Current Job API: Review how the job portal currently fetches and filters jobs. If there’s an existing REST or GraphQL endpoint that accepts query parameters (e.g., GET /jobs?location=Tel+Aviv&skill=React&remote=true), determine if it meets our needs. If not, plan to extend the back-end API. We likely need an endpoint that the chatbot (or any client) can call with various filters combined. Define the API contract: input parameters (location, keywords, company, job type, etc.) and output (list of job listings, possibly paginated). Ensure it can handle multiple values (e.g., maybe multiple keywords or companies).

                              2. Design Filter Logic: Implement or refine the logic to filter jobs based on the structured criteria. Using MongoDB Atlas as an example database: if jobs are in a MongoDB collection, you can use Atlas Search (text indexes for keywords) combined with field filters. For instance, a text search on title/description for “React” AND a field filter for location “Tel Aviv” AND a boolean or field for remote. If the data is in SQL or another store, write the appropriate queries (with indexes on relevant columns for performance). Plan for partial matches (e.g., search “dev” should match “developer” – a text search can handle this via stemming).

                              3. Implement API Endpoint: Develop the new API route (e.g., a REST endpoint /api/chat-search or reuse an existing search endpoint but with JSON request support). Using a modern framework (Express.js, FastAPI, Next.js API routes, etc.), parse the incoming request (which might be a JSON payload of filters from the chatbot service or query params). The endpoint will call the database or search service with those filters and return a JSON list of jobs. Include supportive metadata like total results count, maybe a summary of filters applied (for logging or display). Make sure to sanitize inputs and handle errors: e.g., if an invalid filter value is provided, return a clear error message.

                              4. Support Combined & Semantic Queries (if needed): For MVP, exact field matching and text search on title/description might suffice. But consider enhancements: using an embedding-based semantic search so that, for example, a query “node.js backend” can match a job posting that says “NodeJS developer”. MongoDB Atlas Search offers synonyms and could be configured for common tech synonyms. If that’s complex, note it as a future improvement. At minimum, design the API to accept a free-text query in addition to structured fields, to fall back on broad matching if needed. (This could simply search the overall text if the LLM output doesn’t neatly fill specific fields.) This dual approach ensures that even if the NLP mis-classifies something slightly, the API might still retrieve relevant results via a general text search.

                              5. Pagination & Limits: Decide on how many jobs to return and implement pagination or limits to avoid overload. For example, the API might return the top 10 jobs by relevance. The chatbot can then say “I found 25 jobs, showing 10” and could offer to show more if user asks. Implementing pagination parameters (page number or cursor) in the API now will make it easier to add that feature. This is part of being production-ready: avoid dumping hundreds of results at once.

                              6. Performance Considerations: Ensure indexes (or equivalent) exist on all fields you will filter by (location, company, etc.), and test the query execution plan for efficiency. If the database is large, consider caching frequent queries or results. However, given the dynamic nature of queries from conversation, caching might be less hitful unless many users ask similar broad things like “show all remote jobs”. Still, design with scalability in mind – e.g., the API should be stateless and horizontally scalable if needed (multiple instances connecting to the same DB).

4. Chatbot Development and Integration (UI, Conversation Handler, NLP)
Detailed Steps:
                                             1. UI Integration: Design and implement the chatbot UI within the job portal. Typically, this is a chat widget or panel that can be toggled by the user. For example, a chat icon on the bottom-right that expands into a chat window. Build this with accessibility in mind: use a proper <button> for the chat toggle (so it’s focusable by Tab key)a11y-guidelines.orange.com, ensure the chat window has roles like aria-live or role="log" for messages so screen readers announce new messages, and overall follow WCAG guidelines (high contrast, visible focus states, etc.)blog.aiwarmleads.app. The chat interface should show a transcript of messages (user and bot), and an input box for the user to type queries. Basic features like scrolling through history, and maybe a way to close the chat, are included. Keep the design consistent with the portal’s branding and make the chatbot’s presence clear (e.g., a title “Job Assistant”).

                                             2. Conversation Handler (Backend): Develop the core chatbot logic on the server side. This is the “brain” that receives user messages and returns a response. Steps for each user query: (a) Interpret the message – likely by invoking GPT-4. You’ll call the OpenAI API with a prompt or function call setup that includes the conversation history (for context) and the function definition for job search. The model’s job will be to either directly return a response or decide to call the search_jobs function with parsed parameters. (b) Invoke Job Search: If using function calling, GPT-4 will return a function call with arguments (e.g. search_jobs{"location": "Tel Aviv", "keywords": "React", "remote": true}), which your code should catch. Your code then calls the backend API from Phase 3 (or directly queries the DB) with those parameters. (c) Formulate Bot Reply: Take the results (list of jobs) from the API and convert them into a conversational response. This could be a simple summary (“Found 5 jobs for React developer in Tel Aviv at Google, displaying the first 3: …”) followed by short details of the top results. Alternatively, the chat UI might directly render the job cards from the data and the bot message just says “Here are the jobs I found:”. Decide on the format and implement it. You might feed the job results back into GPT-4 to have it summarize or format nicely (especially if you want the bot to list them in a nice textual way). Ensure the format is not too verbose – users can see the job cards for details, so the bot might just highlight titles or ask a follow-up (“Let me know if you want to refine these results further.”).

                                             3. NLP Integration (GPT-4 & LangChain): Set up the OpenAI API calls. Use GPT-4 model (which understands complex instructions well). Construct a system prompt that instructs the assistant on its role: e.g., “You are a job search assistant. You help users find jobs by converting their requests into filters and showing relevant jobs.” Include guidelines in the prompt about format (maybe “respond with a brief sentence and if results are available, list top 3 job titles with their company and location”). Also define the function for search_jobs with a proper JSON schema for parameters (location, keywords, company, etc.). Let the model know it should use that function when appropriate (OpenAI function calling allows auto mode which will let GPT decide when to call itelastic.co). Use LangChain if it simplifies handling the conversation – for instance, LangChain’s ConversationChain with memory can maintain the chat history easily, and its tool interface can register the search function. This would orchestrate GPT calling the function and getting a result. However, using the OpenAI API directly with function calling might suffice without a full LangChain, since the logic is straightforward (one tool). Evaluate which approach is more convenient for your team.

                                             4. Multi-turn Context & Memory: Implement conversation memory so the chatbot can handle follow-up queries gracefully. If using LangChain, you can plug in a memory like ConversationBufferMemory or a database-backed memory for persistence. If doing manually, maintain a list of the last few messages (both user and bot) and include them in each new prompt to GPT-4. Keep the history limited to avoid hitting token limits (GPT-4 can handle a lot of context, but you might not need entire history always – perhaps just the last few turns and a summary of earlier ones if needed). For example, if a user initially filtered by “React jobs in Tel Aviv” and then says “What about in London?”, the conversation handler should either explicitly catch this by checking if the new input lacks a role/skill but mentions a new location, or rely on GPT-4 to infer it from context. With function calling, GPT has the history, so it might output a function call with the previous parameters adjusted (location changed to London). Make sure to test that. In case GPT doesn’t retain perfectly, you might programmatically store the last filters (when a function call is successful) and on a follow-up, if GPT returns no function (just text), you could merge the last filters with new ones and force a new search. These design choices ensure “the second one” issue (referring to previous results) is handled via short-term memorymedium.com.

                                             5. Error Handling & Fallbacks: Integrate robust error management in the conversation loop. This includes: if the OpenAI API call fails (network issue, rate limit, etc.), catch the exception and respond to the user with a friendly error message (and maybe log the error for devs). If the LLM returns an unhelpful response (e.g., it misunderstood and gave a bizarre answer or didn’t use the function when it should have), have a fallback: you could either try rephrasing the prompt or just say “I’m sorry, I didn’t get that. Could you rephrase or try a different query?”tencentcloud.com. Also handle the case of no results from the job API – the bot should say “No jobs found for those criteria” and perhaps suggest trying different keywords. Implement a fallback for off-topic queries: detect if the function call doesn’t make sense or the user asks something totally unrelated to jobs (the model might either not use the function or return some off-the-cuff response). In such cases, it’s best to respond with a polite statement of inability (and maybe guide back to job search topics). The fallback strategy can be tiered: first a generic “I can’t help with that”tencentcloud.com, second time maybe suggest they use the portal’s search manually or contact support, etc., and if multiple failures, consider ending the conversation or escalating (though in job search context, escalation might not apply as there’s no human agent for this function). The key is to never leave the user at a dead-end – always provide a suggestion for next action even on errors.

                                                * Frontend: Use the existing front-end tech of the portal. If it’s a React app, create a <Chatbot> component. The logic will involve asynchronous calls (to OpenAI and to the job API). Choose an approach to manage these calls – e.g., async/await in Node or Python’s asyncio. If using streaming, ensure the front-end can consume a stream (WebSockets or Server-Sent Events). This can be an enhancement; initially, you could do a simple full message reply.

If using LangChain, it can abstract some of this – for example, you can define a Tool that wraps your job search API and an Agent that uses that tool. LangChain will handle the loop of LLM deciding to call the tool and then incorporate the tool’s result into the next LLM response. This can simplify coding at the expense of an additional dependency. Given this is a focused use-case, many teams opt to call the OpenAI API directly (with function calling, we might not need the full power of an agent framework).

Since job searches aren’t highly sensitive data, storing short-term history on the server or in the client is acceptable, but still abide by privacy (don’t log full conversations with personal info inadvertently).

6. Testing Strategy (Unit, Integration, E2E)
Detailed Steps:
                                                                                    1. Unit Testing (Component-level): Identify the smallest testable units in the system and write tests for them. These include: the function that parses user input to filters (if separate), the backend filtering logic (e.g., does the query builder include the right fields given certain inputs), and any helper functions (like one that merges new filter criteria with old ones for context). Also, test the UI utility functions if any (for example, a function that formats the date or job snippet for display). Use a testing framework appropriate to your stack (Jest/Mocha for Node, PyTest for Python, etc.). Aim to simulate both expected inputs and edge cases. For instance, unit test that the parser correctly handles input like “C# jobs” (might be tricky due to the symbol) or that the fallback mechanism chooses the right response after 3 unknown inputs. These tests ensure your core logic behaves correctly in isolation.

                                                                                    2. Integration Testing (Multiple components together): Now test the interplay between components without the UI. This typically means running the chatbot backend logic with a stubbed or test database. For example, spin up the application in a test mode where it uses a in-memory job list. Then simulate a chat sequence: call the chat endpoint with a certain message and inspect the response. This can be done by sending HTTP requests to the dev server or, for a more controlled approach, by invoking the handler function directly in a test (if your design allows that). Integration tests should cover: a full query that results in function call and job results, a query that results in no jobs, a follow-up query scenario (multiple calls in sequence to ensure context is maintained), and error cases (you might simulate an OpenAI API failure by monkey-patching the call to throw an error in test, then see that your endpoint returns a graceful message). By using integration tests, you verify that your system’s parts (LLM parsing, DB querying, response formatting) work together as expected.

                                                                                    3. End-to-End Testing (E2E): This is testing the system from the user’s perspective through the UI. Utilize tools like Cypress or Playwright for web E2E tests. Write a scenario: “User opens the demo portal, clicks the chatbot icon, asks for a job, sees results.” The test would automate a browser, ensure the chat widget appears, input a query (maybe with typing simulation), and then wait for the response. Then check that certain expected elements appear, for example, that job cards on the page update with filters or that the chat window shows a response containing a job title that matches the query. E2E tests are crucial for catching any integration issues between front-end and back-end (like CORS issues, or mistakes in hooking up the UI to the backend). They also ensure your acceptance criteria from phase 1 are met in a real browser environment. Make sure to include an E2E test for accessibility if possible – e.g., using Axe or other accessibility testing library to scan the chat component for issues (some E2E frameworks have plugins for this).

                                                                                    4. Performance and Load Testing: Given this is a job search feature, you might anticipate times of higher load. Use a tool or simple script to simulate multiple users querying simultaneously. For example, with JMeter or a Node script using axios, fire, say, 50 concurrent requests to the chat endpoint (with a realistic query). Monitor response times and see if any errors occur (like timeouts or rate limits from OpenAI). This will reveal bottlenecks. Perhaps the OpenAI calls are the slowest part (likely), in which case you ensure you’ve enabled any available throughput optimizations (like reusing connections, or if using Azure OpenAI with a higher rate limit). If the load test shows memory issues or such (e.g., if you keep too much conversation history server-side), that’s important to catch now. Define performance thresholds (e.g., the system should handle 20 concurrent chats without degradation, each response under 5 seconds on average).

                                                                                    5. User Acceptance Testing (UAT): In addition to automated tests, it’s good to run a UAT session. Get a few actual users or stakeholders to use the chatbot on a staging environment. They might find conversation flows that are awkward or edge cases not thought of. Have them follow a script of tasks (like “find a job in X, then refine by Y, then do Z”) and also do exploratory testing (ask weird questions, or try to “break” the bot with long input or special characters). Gather their feedback and logs from these sessions. This will validate that the system meets the real-world requirements and is intuitive. Often, UAT will lead to minor tweaks in phrasing or behavior that aren’t code “bugs” but improvements.

Technologies & Tools:
                                                                                       * Testing Frameworks: Use Jest for unit/integration tests if in Node.js (it’s versatile and supports mocking easily). If Python, PyTest is great. These frameworks allow test suites that can be run in CI. For E2E, Cypress is popular for web apps and has good support for simulating user interactions and even intercepting network calls. Playwright is another option with a more developer-centric approach and can do headless or headed browser tests.

                                                                                       * Mocking and Stubbing: Utilize libraries like nock (Node) to mock external HTTP calls (e.g., you don’t want your tests to actually call OpenAI or real DB). Instead, intercept the OpenAI API call URL and return a canned response (like a prepared function_call JSON) to simulate GPT’s behavior. This way, tests are deterministic and don’t depend on API keys or network. Similarly, use an in-memory or test database to not touch production data. For example, MongoDB Memory Server can spin up a temporary Mongo instance for tests with sample data.

                                                                                       * Continuous Integration (CI): Set up tests to run in CI (GitHub Actions, etc.) on each commit. This ensures nothing breaks as development progresses. Copilot can help write the CI config (like a YAML to run npm test or pytest). Ensure the CI environment has necessary secrets for any integration (if you decide to hit a dev OpenAI environment, though better to mock it).

                                                                                       * Accessibility Testing Tools: Apart from manual testing, integrate something like axe-core in your tests. There’s cypress-axe plugin that can run an accessibility scan on a page in an E2E test. This will flag if contrast is low, ARIA roles missing, etc. It’s easier to fix those early.

                                                                                       * Monitoring in Tests: You might not fully set up monitoring yet, but you can test that your logging or error capturing is working. For instance, if you have a logger, verify in a test that a known error triggers a log entry. This is not user-facing, but it ensures your monitoring hooks (discussed in Phase 8) are in place.

                                                                                          * Test Generation: Copilot can draft test cases. Testing & Validation (what to verify):
                                                                                             * All tests must pass. Check off each requirement against a test case. If any requirement isn’t testable easily (like “response time < 2s”), consider adding at least a performance assertion in a test or monitoring (maybe not fail the test if it’s slightly over, but measure it).

You might simulate this in a test by forcing the OpenAI call to return an error, and verify your code handles it (perhaps by wrapping the OpenAI call in a function you can stub to throw an exception in test).

                                                                                             * Exit Criteria for Testing Phase:

                                                                                                * Comprehensive Test Suite: We have unit tests covering parsing, filtering logic; integration tests covering full chat flow with mocked external calls; E2E tests covering actual user scenarios in the browser.

7. Deployment and Production Readiness
Detailed Steps:
                                                                                                      1. Infrastructure & Environment Setup: Prepare the environment where this chatbot will run in production. This could be deploying to a cloud platform (AWS, Azure, GCP) or a managed service. If the job portal is already hosted (say on AWS EC2 or a container service), integrate the chatbot service into that. You may containerize the application for consistency. Create a Dockerfile for the app (Copilot can assist here, e.g., choosing a lightweight Node image, installing dependencies, exposing ports). Ensure to separate config from code: the OpenAI API keys, database URLs, etc., should come from environment variables, not hard-coded. Set up those secrets in the deployment environment (e.g., in AWS Secrets Manager or as environment variables in your container orchestration).

                                                                                                      2. AI Headhunter Chatbot with OpenAI MCP and MongoDB
Project Overview and Goals
This project implements an AI-powered recruiting chatbot that interacts with job seekers in a human-like conversation. The chatbot leverages OpenAI's Model Context Protocol (MCP) to securely access a MongoDB database of jobs and candidates, enabling it to provide personalized job recommendations and perform database actions (like searches and applications) via natural language commands. The end goal is a conversational headhunter assistant that can:
                                                                                                                                                   * Discuss the user’s experience, skills, and preferences in a friendly, interactive chat.

                                                                                                                                                   * Query the MongoDB job database based on the candidate’s profile (location, skills, experience) to find suitable openings.

                                                                                                                                                   * Present relevant jobs to the user, allow them to request more details or apply to a chosen job.

                                                                                                                                                   * Handle CV uploads or LinkedIn profile links by extracting key information and using it to refine job matches.

                                                                                                                                                   * Encourage the user to register/login (standard email or OAuth) when needed – for example, to save jobs or submit an application – and then record the user’s actions (like saving a job or applying) back to the database.

By combining a React frontend with an OpenAI MCP-driven backend, this chatbot will behave like a personable recruiter: remembering user details, searching the latest jobs, and guiding the candidate through the job-finding process. All design decisions follow best practices in AI agent integration and web development, which we’ll explain and justify below.
Architecture and Tech Stack
Tech Stack & Components:
                                                                                                                                                      * React Frontend: A web application providing the chat UI and user authentication interface. It manages user input/output, file uploads (CV), and login/signup flows. The UI will display chatbot messages (including formatted job listings) and allow user actions (selecting a job, etc.).

                                                                                                                                                      * Backend AI Agent: A server (built in Python using OpenAI’s Agents SDK, or Node.js with OpenAI’s API) that hosts the AI logic. This agent uses GPT-4 (via OpenAI API) as the Large Language Model and is configured with tools (via MCP) to interact with external data.

                                                                                                                                                      * OpenAI Model Context Protocol (MCP): The standard layer enabling the LLM to access external resources securely. We will run a MongoDB MCP Server to expose the job database to the AI in a controlled mannerGitHubblog.logrocket.com. The MCP server acts like a “USB-C port” for the AI – it standardizes how the model can retrieve or write data (jobs, user info) without hard-coding database logicGitHub.

                                                                                                                                                      * MongoDB Database: Stores job postings (with fields like title, description, location, required skills, etc.) and candidate data (user profiles, resumes, saved jobs, applications, etc.). We assume this is pre-populated with job data (as provided via CSV) and will also store any new user info or applications. The MongoDB MCP server allows read and write operations on this database as “tools” the AI can invoke (e.g. find jobs, insert an application)blog.logrocket.com.

                                                                                                                                                      * Authentication & User Management: Users can chat as guests initially, but to apply or save jobs the chatbot will prompt login. We use a standard email/password registration (with proper hashing & JWT sessions) or OAuth (e.g. LinkedIn) for convenience. The frontend handles the auth UI, and the backend verifies credentials and associates actions with a user ID.

High-Level Flow: When a user interacts, the front-end sends their message (and possibly session info like login status or uploaded CV data) to the backend agent. The agent, guided by a system prompt and conversation history, decides how to respond – it may answer directly or invoke a tool via MCP to fetch data before respondingblog.gopenai.comblog.logrocket.com. For example, if the user asks “Find me remote Python jobs in New York,” the agent will call the MongoDB tool to query jobs matching those criteria, then format the results into a friendly reply. The response is sent back to the frontend to display. This architecture separates concerns cleanly: the UI is decoupled from AI logic, and the AI uses MCP integrations for database access instead of insecure direct queriesGitHub.
MongoDB MCP Server Integration
At the core of our backend is the MongoDB MCP Server, which exposes database operations as API-like tools the LLM can use. We will use the official MongoDB MCP server packageblog.logrocket.com, configured with our connection string and launched alongside the agent. Key setup steps:
                                                                                                                                                         * Installation: The MongoDB MCP server is available as an NPM package (mongodb-mcp-server). We can run it via npx for simplicity. Ensure Node.js 20+ is installed (a prerequisite for MCP servers)github.com. We also need a MongoDB URI with credentials for the database (or Atlas API keys)github.com.

                                                                                                                                                         * Secure Configuration: Rather than hard-coding the connection string, we follow best practices by using environment variables for sensitive infogithub.com. For example, we set MDB_MCP_CONNECTION_STRING in the environment. The server can pick this up, or we pass it as an argument. We will enable write access (no --readOnly flag) since the bot must insert application records – by default MCP servers run read-only for safetygithub.com. (We only remove this restriction after ensuring our agent is well-behaved.)

                                                                                                                                                         * Launching the Server: We have two options:

Via MCP Client (Preferred): Use OpenAI’s Agents SDK or LangChain MCP adapter to spawn and manage the MCP server process from our code. For example, in Python we can use MCPServerStdio to launch the server as a subprocess and communicate via STDIOblog.logrocket.com. In our case, we’d do:

from openai.experimental.mcp import MCPServerStdio


# Launch MongoDB MCP server with connection string from env
mcp_server = await MCPServerStdio(params={
    "command": "npx",
    "args": ["-y", "mongodb-mcp-server", "--connectionString", os.getenv("MDB_MCP_CONNECTION_STRING")]
}).__aenter__()
                                                                                                                                                            *  This asynchronously starts the server and makes its tools available to the agent. We see a similar pattern in community examples where MCP servers (BrightData, Prisma, etc.) are started via codedev.toblog.logrocket.com. Using the SDK’s built-in launcher ensures the server lifecycle (startup/shutdown) is tied to our app and avoids manual process management. After launching, we will have a handle to the mcp_server and can retrieve its tools schema.

Via Config File: Alternatively, in a Node environment (e.g., VS Code, Copilot Chat) one can declare the server in an mcpServers config. For instance, a JSON config snippet in .vscode/mcp.json might be:

{
  "mcpServers": {
    "MongoDB": {
      "command": "npx",
      "args": ["-y", "mongodb-mcp-server", "--connectionString", "mongodb+srv://user:pass@cluster/myDB"]
    }
  }
}
                                                                                                                                                               *  This is how a tool like VSCode Copilot would know to spin up the serverblog.logrocket.com. In our case, since we’re building a custom backend, we prefer method (1) programmatically.

                                                                                                                                                                  * Supported Tools: Once running, the MongoDB MCP server provides a suite of Tools (analogous to API endpoints) for common DB operationsblog.logrocket.com. These include:

                                                                                                                                                                     * list_databases, list_collections, collection_schema – introspection tools (the agent can learn DB structure if needed).

                                                                                                                                                                     * CRUD operations: find (with query filter), aggregate (with pipeline), insertOne, updateOne, deleteOne, etc., scoped to collections. For example, the agent can call a find tool on the “jobs” collection with a filter object to retrieve matching job documents. All tool inputs/outputs are in structured JSON format.

                                                                                                                                                                     * If using MongoDB Atlas, there are also Atlas management tools (like listing clusters), but our use case mainly needs the database tools.

These tools let the AI retrieve data by natural language intent, without hardcoding queries. For instance, an AI request "Show me backend engineer jobs in London" can be translated into a find on the jobs collection with { "title": /Backend Engineer/i, "city": "London" } behind the scenes. The beauty of MCP is the AI agent can figure out the needed tool call and execute it during conversationblog.logrocket.com, then incorporate results into its reply.

In summary, by running the MongoDB MCP server in our backend, we expose the job data to the AI agent through a safe, standardized interface. Next, we’ll see how the AI agent uses these tools to conduct the conversation logic.
Backend AI Agent Design (OpenAI MCP Integration)
The AI backend orchestrates the conversation between the user and the LLM (GPT-4) with access to the database tools. We will implement this as an asynchronous service (using Python’s FastAPI or Flask for HTTP endpoints). Key aspects of the backend:
OpenAI Agents SDK and Tool Usage
We use OpenAI’s Agents SDK, which provides abstractions for defining agents, tools, and multi-step workflows. The Model Context Protocol is directly supported in the SDK, making it straightforward to register our MongoDB MCP server as a tool sourceblog.logrocket.com.
Agent Setup: We create a single primary agent (let’s call it the JobAssistantAgent) with the following configuration:
                                                                                                                                                                        * LLM Model: GPT-4 via OpenAI API. We choose GPT-4 for its superior capability in understanding context and producing coherent, nuanced responses. The Agents SDK allows using OpenAI ChatCompletion models. For example, we initialize the model with model = ChatOpenAI(model="gpt-4-turbo", temperature=0)blog.gopenai.com. Setting a low temperature (0–0.2) is important here to ensure the agent stays factual and uses the tools deterministically rather than hallucinatingblog.gopenai.com.

System Prompt (Role Instructions): We craft a detailed system message that primes the assistant to act as a recruiter/headhunter. This prompt guides the agent’s tone and strategy. For example:

"You are an AI career assistant helping a job seeker find their ideal job. 
 Speak in a friendly, professional tone as a human recruiter would. 
 Ask the user about their experience, skills, and preferences. 
 Use the tools at your disposal to search our jobs database (do not guess data). 
 When presenting jobs, include title, company, location, and highlight why it's a good match (based on the user's profile). 
 If the user asks to apply or for more info on a job, you may use database tools to retrieve details or record their interest. 
 ALWAYS encourage the user to sign up or log in before proceeding with an actual application (for example, say 'Please log in to apply'). 
 Ensure each answer is helpful and concise."
                                                                                                                                                                           *  These instructions ensure the AI understands its role and the integration points (like prompting for login) in conversation. (We include the rule about login because the agent needs to know to handle unauthenticated users by asking them to register – this is a business rule provided in the prompt.) By defining this system context, we align the AI’s behavior with our requirements. Similar structured instructions are used in other agent examples to constrain their outputdev.todev.to.

                                                                                                                                                                           * MCP Tools Integration: We attach the MongoDB MCP server to the agent. In the Agents SDK, this is often done by specifying mcp_servers=[mcp_server] when constructing the agentdev.todev.to. This means all tools from that server (like find, aggregate, etc.) become available to the agent. The agent can then decide during conversation to use these tools. For example, if the user asks a question that requires data, the agent will internally formulate a tool call.

How the agent knows about tools: The MCP server provides a schema of available tools (with names and input args). The Agents SDK fetches this, so the LLM is aware of what functions it can callblog.gopenai.com. We may explicitly retrieve tools via something like tools = await client.get_tools() (as in LangChain adapter usageblog.gopenai.com) or rely on the Agent to do it. Either way, before responding to a user prompt, the GPT-4 model is fed a context that includes tool specifications (in a format similar to OpenAI function calling or JSON schema). This setup is handled by the SDK behind the scenes.

                                                                                                                                                                           * Conversation Handling (ReAct Loop): The agent uses the ReAct (Reason+Act) patternblog.gopenai.com to decide on actions. In practice, each time the user sends a message, we will call something like agent.ainvoke({"messages": [ ... ]}) with the conversation (or last query)blog.gopenai.com. The agent (GPT-4) will “think” in steps: it can output a hidden reasoning trace like: “Thought: The user is asking for X, I should use the find tool”, then an Action: call a tool with certain arguments, then see the Tool’s Observation (result), and finally produce an Answerblog.gopenai.com. This all happens within one API call cycle if using OpenAI functions or Agents SDK – the developer just sees the final answer, but under the hood the model may have invoked multiple tools to get there. The ReAct approach is crucial for a stateful query: e.g., Thought: “User asked for jobs requiring skill Y. I will use the find tool to search jobs with that skill.” -> Action: find{collection: "jobs", filter: {must_have: "Y"}} -> Observation: (returns 3 matching jobs) -> Thought: “I got 3 jobs, I'll list them.” -> Answer: (a conversational reply with the 3 jobs). The Agents SDK and MCP make this seamless: the model’s “action” is routed to the actual tool call, then the output is fed back into the modelblog.logrocket.com.

                                                                                                                                                                           * Multi-turn memory: We maintain the conversation context. The simplest approach is to accumulate the dialogue as messages and supply the recent history on each agent invocation (just like a ChatGPT conversation). However, with the agent able to use tools, often we can handle each user query independently since the database can be queried for context. Still, for a natural experience, we include at least the last few interactions so the agent remembers what the user has told about their background or preferences. This can be done by storing history on the server side (in memory or even persisted if we want continuity between sessions) and sending it in the agent.invoke call. The OpenAI Agents SDK supports maintaining state if needed, but we'll implement a controlled memory to avoid context window issues.

                                                                                                                                                                           * Error Handling: We wrap tool calls in try/except on the server side. If the MCP server is unreachable or a query fails, the agent should catch that exception. In our MCPServerStdio setup, launching the server inside a try/except and using asyncio.wait_for with timeout (as seen in community codedev.to) ensures it doesn’t hang forever on startup. Also, the agent can handle “no results” gracefully: e.g., if a find returns empty, we instruct the agent (via prompt or few-shot example) to apologize and perhaps broaden the search.

Agent Workflow Example: To illustrate, here’s how a typical query flows through the agent:
User says: “I have 5 years of experience in Python and live in Tel Aviv. I want a remote backend job.”
                                                                                                                                                                              1. The system prompt + conversation so far is given to GPT-4. The user’s message triggers the agent.

                                                                                                                                                                              2. Reasoning: The agent deduces it should search the jobs DB for roles matching “backend”, requiring Python, located in Tel Aviv or remote.

                                                                                                                                                                              3. Tool Action: Agent calls find tool via MCP:

                                                                                                                                                                                 * Tool: find on collection jobs

                                                                                                                                                                                 * Arguments: a filter like { $or: [ {city: "Tel Aviv"}, {remote: true} ], profession: /backend/i, must_have: /Python/i }.
This uses the MongoDB query language, which the agent can formulate thanks to the tool schema and natural language-to-JSON reasoning (the agent is trained on patterns for using these tools). Note: We might provide the agent with the exact field names (e.g., must_have skills are pipe-separated strings per the CSV) via documentation or collection_schema toolblog.logrocket.com so it knows how to query effectively.

                                                                                                                                                                                    4. Observation: The MCP server executes the query on MongoDB and returns results (e.g., 2 job documents that match). The agent sees these results (likely truncated or summarized if large).

                                                                                                                                                                                    5. Answer: The agent composes a reply: e.g., “I found a couple of positions that might interest you: 1) Senior Backend Engineer at Acme Ventures (New York, Remote) – requires Python, FastAPI, PostgreSQL. 2) Backend Developer at Innovate Labs (Remote) – requires Python, stakeholder management, etc. Both are remote-friendly. Let me know if you'd like more details or to apply!”

                                                                                                                                                                                       * The job details in the answer come directly from the DB query results (ensuring accuracy). The tone is enthusiastic and helpful, as a recruiter would be. The agent might also mention how the user’s 5 years experience fits (drawing from the conversation context).

                                                                                                                                                                                       * All this is generated by GPT-4 after it got the data. We maintain citations in logs but the user doesn’t see JSON or raw data – just the friendly text.

This cycle repeats for each user prompt. If the user asks follow-up like “Can I see more about job 1?”, the agent can call a tool (maybe find or a getJobById if we provide one) to retrieve the full description of that job, then summarize or quote it in the answer. The conversation flows naturally, with the AI deciding when to use the database.
Handling Applications and User Data
When the user is ready to apply for a job, the agent needs to: (a) ensure the user is logged in, and (b) record the application or provide next steps. We implement this as follows:
                                                                                                                                                                                          * Login Check: The frontend will send the agent a flag or the user’s ID if authenticated. We can incorporate this into the system context (e.g., a system message like <UserLoggedIn:true> or simply have the backend know it). The agent’s instructions already include “always encourage login when applying”, so if UserLoggedIn:false and the user says "I want to apply to Job 1", the agent will respond with something like “Sure! To proceed with the application, please log in or create an account. I can wait while you do that.”. This prompt originates from our business rule in the system prompt. The frontend can detect this message and trigger a login modal. Once the user logs in, we inform the agent (perhaps by calling it again with an update like “User has logged in.” or simply by setting the internal flag). Then the user can repeat "I'm logged in, apply me to Job 1."

                                                                                                                                                                                          * Applying / Saving in DB: Assuming the user is authenticated (we have their userID from our auth system), the agent can now perform a write. For example, we may have a collection applications where we store { job_id, user_id, timestamp, status:"applied" }. The agent can call the insertOne tool provided by MongoDB MCP to create this recordblog.logrocket.com. E.g., insertOne with document={"user": "<userid>", "job": "<jobid>", "action": "applied", "time": "<now>"} in an applications collection. Alternatively, we could update a user profile document to add the job to their “applied” list. All such operations are possible through MCP tools (since we allowed write access).

                                                                                                                                                                                          * Confirmation to User: After writing, the agent would respond with a confirmation, e.g., “Great, I've noted your application for Senior Backend Engineer at Acme. The company will reach out if there's a fit! I've also emailed you the application link for reference.”. We can have the agent include next steps or tips (making the experience more human). The actual emailing can be another tool (for instance, if we had an SMTP or SendGrid MCP tool – but that’s beyond scope; it could also be handled by our backend outside the AI). The key part is the DB now reflects the user's interest.

                                                                                                                                                                                          * Resume Uploads: If the user uploads a CV, the frontend will send the file (or extracted text) to the backend. We will likely preprocess this – for example, use a Python PDF parser to get text. We then feed the text (or a summary of it) to the agent as if it were user-provided information. The agent can then extract skills/experience from it. In fact, we could have a specialized prompt or tool for parsing resumes, but a simpler approach is to say: “User’s CV: [full text]” as a system message and instruct the agent to use it. GPT-4 is capable of summarizing and picking out key qualifications. The agent can then do a database search based on the CV (e.g., identify top 3 skills or the last job title from the CV and query related jobs). This effectively automates the job matching. Optimization: For large resumes, we might use a separate LLM call or LangChain text splitter + vector search to find relevant job requirements, but given our scope, we rely on GPT-4’s ability to handle a few pages of resume text within its context window (8K or 32K tokens) – this should suffice for typical resumes.

Integration Considerations and Validation
Every decision above is geared towards robustness and clarity:
                                                                                                                                                                                             * Using MCP ensures the LLM only accesses data we allow. It standardizes the interface and is adopted by major platforms, making our solution future-proofGitHub. We avoid ad-hoc scraping or insecure DB connections from the LLM. This aligns with best practices for tool-augmented AI: “MCP doesn't reinvent the wheel... It just aims to standardize how AI applications interact with external systems”GitHub. By using the official MongoDB MCP server, we benefit from a well-tested integration maintained by MongoDB (including support for Atlas, etc.).

                                                                                                                                                                                             * The OpenAI Agents SDK gives us a structured way to manage the agent’s chain-of-thought and tool use. This avoids writing our own prompt-chains and parsing tool calls. As noted in OpenAI’s documentation, Tools (like our DB operations) “let agents take actions: things like fetching data, running code, calling external APIs…”openai.github.io. We leverage this to let GPT-4 fetch data rather than guessing. The multi-step workflow we described (profile analysis -> job search -> summary) is inspired by a real multi-agent pipelinedev.todev.to, but for simplicity we keep one agent that can handle all steps. We validated this approach with a smaller LangChain example where a single ReAct agent was able to list databases and answer questions by iterative tool useblog.gopenai.com.

                                                                                                                                                                                             * No hard-coded SQL/queries: The agent dynamically builds queries. This is more flexible as the same system can adapt to different user requests (filter by city, filter by skill, etc.) in free-form. Our only requirement is to ensure the agent has correct field info. We can do an initial tool call like collection-schema on “jobs” so the agent sees fields like title, city, must_have skills, etc. That way it knows how to filter properly. This mirrors how one would let an AI browse an API spec before usage.

                                                                                                                                                                                             * Ensuring relevant results: We might add a scoring mechanism if needed (like vector similarity between job description and resume via embeddings), but that’s an enhancement. Initially, a combination of keyword filters (provided by user input) is effective. The agent can also do an aggregate with a more complex pipeline if needed (for example, sorting by recency or doing a text search). The MongoDB MCP supports complex queries – e.g., an aggregation pipeline can be invoked as shown in docsblog.logrocket.com. We could instruct the agent to use those for advanced matching (this is an area to iterate during testing).

                                                                                                                                                                                             * Testing and Debugging: During development, we can run the chatbot in a controlled environment (e.g., using a test conversation) and inspect the agent’s actions. The Agents SDK allows logging the tool calls. We will verify that when a user asks for jobs, the agent indeed calls find with reasonable filters, and when a user says "apply", the insertOne is called. This end-to-end test ensures no bugs in the tool invocation logic. Because we use well-documented interfaces, the risk of logical bugs is low – any mistakes (like wrong field name) can be caught by observing the agent’s errors and correcting prompts or providing better context.

React Frontend Implementation

The server responds with a confirmation or extracted summary.

                                                                                                                                                                                                            * We then send a message into the chat from the user that says something like: "I've uploaded my CV." The bot then responds with something like, "Thanks for the CV. I see you have experience in X. Let me find some matches..." followed by a job search.

                                                                                                                                                                                                            * We ensure to handle file size limits and show progress if needed. (This part will rely on typical file upload handling and is not MCP-specific, so we won’t dive deep here.)

                                                                                                                                                                                                               * Authentication UI: We’ll create components for Login and Signup, perhaps modals that appear over the chat or a separate page route. Using a popular library (like Firebase Auth UI or custom form with validation) ensures best practices:

On success, store auth token (JWT) in memory or cookie. We then update state to reflect isLoggedIn:true. Integration with Backend API:
We expose REST endpoints in our backend:
                                                                                                                                                                                                                        * POST /api/chat: accepts {message: "user's message", userId: optional} and returns {reply: "assistant's reply"}. The backend handler for this will call our JobAssistantAgent (as described) and produce a response. We include the userId or a session token so the backend knows who is talking (for context like login or personalized data). The backend might also attach additional info before invoking the agent – e.g., if a CV was just uploaded, attach a summary of it.

                                                                                                                                                                                                                        * POST /api/uploadCV: handles file upload, possibly returns a status. The text extraction can be done here and maybe stored in Mongo (e.g., in a candidates collection under the user’s profile). The chatbot doesn’t directly use this endpoint; it’s more for preprocessing. After a successful upload, we could automatically call the chat endpoint with a message like "CV_UPLOAD_DONE" that triggers the bot to acknowledge CV info.

                                                                                                                                                                                                                        * POST /api/register and POST /api/login: standard auth endpoints. On register, create a new user doc in users collection, hash password, etc. On login, verify and return token. These endpoints are outside the AI scope, but we ensure they are secure (rate limiting, input sanitization, etc.).

All these calls happen via fetch from the React app. For example, in our Chat component’s send function:
async function sendMessage(text) {
   addMessage({sender: 'user', text});
   const res = await fetch('/api/chat', {
     method: 'POST',
     headers: { 'Content-Type': 'application/json', 'Authorization': userToken },
     body: JSON.stringify({ message: text })
   });
   const data = await res.json();
   addMessage({sender: 'bot', text: data.reply});
}


This is a simplified snippet. In production, we handle errors (network issues, auth expiry), and maybe use a state manager or React Query for cleaner API integration.

Authentication & User Experience Flow
To tie everything together, here’s a typical user journey and how each part works in concert:
                                                                                                                                                                                                                              1. Landing & Onboarding: User visits the site and sees a welcome from the chatbot. For example, the bot might proactively greet: “Hi there! I'm JobAssistant, your AI recruiter. To get started, you can tell me about your dream job or upload your CV.” (We can program an initial message like this when the component mounts, to prompt interaction.) The user is not logged in at this point (the chat knows this via context).

                                                                                                                                                                                                                              2. User Query (Guest): User types "I'm a data scientist with 3 years of experience, looking for opportunities in NYC." The front-end sends this to /api/chat with no userId (or a guest ID). The backend agent processes it:

                                                                                                                                                                                                                                 * System sees no logged-in user, but that’s fine for searching.

                                                                                                                                                                                                                                 * Agent uses find tool on jobs where location NYC and role matches data scientist.

                                                                                                                                                                                                                                 * Agent replies with a few matches (with bullet points). The text also says “If any of these interest you, let me know! You can also create an account to save jobs.” This line is influenced by our prompt to gently push registration.

                                                                                                                                                                                                                                    3.                                                                                                                                                                                                                                        * Because UserLoggedIn:false, agent responds: “Sure! You’ll need to log in or sign up so I can help with the application process. I’ve opened the login form for you.”

                                                                                                                                                                                                                                       * The front-end, upon detecting this response (we can either parse the text or we know internally that an "apply" action was attempted), triggers the Login modal.                                                                                                                                                                                                                                              * It might also fetch the job details (to confirm title/company).

                                                                                                                                                                                                                                             * The emoji and celebratory tone add a human touch. Follow-up and Profile Use: The user might ask "What did I apply for?" If logged in, the bot can query the applications collection (maybe via a join with jobs) to list their active applications. Either way, the integration shows its value: the AI can pull not just static job data, but also the user’s own data (since it can query any collection we allow).                                                                                                                                                                                                                                                 7. Resume Upload Alternative: If instead of describing themselves, the user uploads a resume at start, the flow would be:

                                                                                                                                                                                                                                                   * User uploads file -> backend extracts text -> perhaps the front-end sends a chat message like "User uploaded a resume."

                                                                                                                                                                                                                                                   * Agent then analyzes the resume text (either by a prompt: “From the resume: [text].” or calling a hypothetical analyze_resume tool if we made one). In one approach, the developer might pre-process the resume into a summary of skills to reduce token usage, then feed that summary as system context.

                                                                                                                                                                                                                                                   * The agent responds with a personalized greeting: “Thanks for sharing your resume! I see you have experience in Machine Learning and Python. I’ll use that to find suitable roles.” and proceeds to search the DB for matching jobs (using skills from resume as keywords). This is similar to how an example agent workflow was described for LinkedIn profile analysis and job matchingdev.todev.to, except here we use resume data instead of a LinkedIn URL.

Throughout this interaction, the user remains engaged through conversation rather than filling out forms or searching manually. The AI provides value by doing the heavy lifting (searching and filtering) and by offering expertise (e.g., it could advise “Your 3 years experience is a bit below the requirement for some roles, but I found a mid-level position that fits.” – such commentary makes it feel like a real recruiter).
Finally, we ensure privacy and security: the MCP server runs within our backend, so the database is not exposed directly to the client or the public. All AI decisions involving data go through controlled tools (with optional logging for audit). If the user asks something unrelated or disallowed (like personal data of other candidates), the system prompt and OpenAI’s content filters would prevent any privacy breach. We also do not feed sensitive personal info to the model unless necessary (and when we do – e.g. resume – it’s at the user’s request).

12.1 matching.get_similar_jobs
# backend/app/services/matching.py
from typing import List, Dict
from collections import Counter


def jaccard(a: set[str], b: set[str]) -> float:
    if not a and not b: return 0.0
    inter = len(a & b)
    uni = len(a | b)
    return inter / uni if uni else 0.0


def title_bonus(t1: str, t2: str, prof1: str|None, prof2: str|None) -> float:
    t1s, t2s = set(t1.lower().split()), set(t2.lower().split())
    word_hit = 1.0 if (t1s & t2s) else 0.0
    prof_hit = 1.0 if (prof1 and prof2 and prof1 == prof2) else 0.0
    return 1.0 if (word_hit or prof_hit) else 0.0


def get_similar_jobs(db, job_id: str, k: int = 5) -> List[Dict]:
    base = db.jobs.find_one({"_id": job_id})
    if not base: return []
    tenant_id = base["tenant_id"]
    base_sk = set(base.get("skill_set", []))
    base_title = base.get("title","")
    base_prof = base.get("profession")


    recs = []
    cursor = db.jobs.find({"tenant_id": tenant_id, "_id": {"$ne": job_id}})
    for j in cursor:
        js = set(j.get("skill_set", []))
        s_sim = jaccard(base_sk, js)
        bonus = title_bonus(base_title, j.get("title",""), base_prof, j.get("profession"))
        score = 0.85 * s_sim + 0.15 * bonus
        if score <= 0: continue
        recs.append({
            "id": j["_id"],
            "title": j.get("title"),
            "city": j.get("city"),
            "overlap_skills": list(base_sk & js)[:5],
            "score": round(score, 3),
        })
    recs.sort(key=lambda x: x["score"], reverse=True)
    return recs[:k]

from fastapi import APIRouter, HTTPException, Depends
from app.core.db import get_db
from app.services.matching import get_similar_jobs


router = APIRouter(prefix="/portal", tags=["portal"])


@router.get("/recommendations/{job_id}")
def portal_recommendations(job_id: str, db=Depends(get_db)):
    job = db.jobs.find_one({"_id": job_id}, {"_id":1,"title":1})
    if not job:
        raise HTTPException(status_code=404, detail="Job not found")
    recs = get_similar_jobs(db, job_id, k=5)
    return {"original_job": {"id": job["_id"], "title": job.get("title")}, "recommendations": recs}


@router.get("/job/{job_id}")
def portal_job_details(job_id: str, db=Depends(get_db)):
    job = db.jobs.find_one({"_id": job_id}, {
        "_id":1,"title":1,"description":1,"must_have":1,"nice_to_have":1,
        "city":1,"is_remote":1,"skill_set":1,"profession":1
    })
    if not job:
        raise HTTPException(status_code=404, detail="Job not found")
    job["id"] = job.pop("_id")
    return job

from pydantic import BaseModel, EmailStr
from fastapi import APIRouter, HTTPException, Depends
from app.core.db import get_db
from app.core.security import hash_password, create_jwt_token


router = APIRouter(prefix="/auth", tags=["auth"])


class RegisterCandidateIn(BaseModel):
    name: str
    email: EmailStr
    password: str
    tenant_id: str


@router.post("/register-candidate")
def register_candidate(payload: RegisterCandidateIn, db=Depends(get_db)):
    exists = db.users.find_one({"tenant_id": payload.tenant_id, "email": payload.email})
    if exists:
        raise HTTPException(status_code=409, detail="User already exists")
    user = {
        "tenant_id": payload.tenant_id,
        "name": payload.name,
        "email": payload.email,
        "password_hash": hash_password(payload.password),
        "role": "candidate",
    }
    db.users.insert_one(user)
    db.candidates.insert_one({
        "tenant_id": payload.tenant_id,
        "full_name": payload.name,
        "email": payload.email,
        "skills": [],
        "resume_url": None,
    })
    token = create_jwt_token({"tenant_id": payload.tenant_id, "email": payload.email, "role": "candidate"})
    return {"token": token, "user": {"name": payload.name, "email": payload.email, "role": "candidate"}}

from app.core.db import get_db
from app.core.auth import get_current_user  # returns dict with tenant_id, email, role

router = APIRouter(prefix="/jobs", tags=["applications"])


@router.post("/{job_id}/apply")
def apply_job(job_id: str, db=Depends(get_db), user=Depends(get_current_user)):
    if user["role"] != "candidate":
        raise HTTPException(status_code=403, detail="Candidates only")
    job = db.jobs.find_one({"_id": job_id})
    if not job:
        raise HTTPException(status_code=404, detail="Job not found")
    if job["tenant_id"] != user["tenant_id"]:
        raise HTTPException(status_code=403, detail="Tenant mismatch")
    cand = db.candidates.find_one({"tenant_id": user["tenant_id"], "email": user["email"]})
    if not cand:
        raise HTTPException(status_code=400, detail="Candidate profile not found")
    db.applications.insert_one({
        "tenant_id": user["tenant_id"],
        "job_id": job_id,
        "candidate_id": cand["_id"],
        "created_at": datetime.utcnow(),
        "status": "new"
    })
    # TODO: notifications.notify_recruiter_application(...)
    return {"success": True}

// frontend/src/components/chat/Chatbot.tsx
import { useEffect, useRef, useState } from "react";
import api from "@/lib/api";
import JobDetailCard from "./JobDetailCard";
import { useAuth } from "@/lib/auth";
import { useNavigate, useLocation } from "react-router-dom";


export default function Chatbot({ tenantCode, jobId, originalJob, recs }) {
  const [messages, setMessages] = useState<{sender:'bot'|'user', text:string}[]>([]);
  const [detail, setDetail] = useState<any|null>(null);
  const [input, setInput] = useState("");
  const endRef = useRef<HTMLDivElement>(null);
  const { user } = useAuth();
  const navigate = useNavigate();
  const location = useLocation();


  useEffect(() => {
    if (!recs || !originalJob) return;
    const intro = [
      { sender: 'bot', text:
        `Sorry this role wasn't a fit: **${originalJob.title}**.\n` +
        `Here are similar openings:\n` +
        recs.map((r: any, i:number) => `${i+1}. ${r.title} (${r.city || 'Location flexible'})`).join('\n') +
        `\n\nReply with a number to learn more, or type "apply".`
      }
    ];
    setMessages(intro as any);
  }, [recs, originalJob]);


  useEffect(() => {
    endRef.current?.scrollIntoView({ behavior: "smooth" });
  }, [messages, detail]);


  const showDetails = async (idx: number) => {
    const r = recs[idx];
    if (!r) return;
    const res = await api.get(`/portal/job/${r.id}`);
    setDetail(res.data);
    setMessages((m) => ([...m, {sender:'bot', text: `Here are details for **${res.data.title}**.`}]));
  };


  const onApply = () => {
    if (!detail) return;
    if (!user) {
      const next = `${location.pathname}${location.search}`;
      navigate(`/login?next=${encodeURIComponent(next)}`);
      return;
    }
    api.post(`/jobs/${detail.id}/apply`).then(() => {
      setMessages((m)=>[...m, {sender:'bot', text:"Application submitted! Good luck 🤞"}]);
    }).catch(()=> {
      setMessages((m)=>[...m, {sender:'bot', text:"Couldn't submit now. Please try later."}]);
    });
  };


  const onSend = (e:any) => {
    e.preventDefault();
    if (!input.trim()) return;
    const msg = input.trim();
    setMessages((m)=>[...m, {sender:'user', text: msg}]);
    setInput("");


    const num = parseInt(msg, 10);
    if (!isNaN(num) && num >=1 && num <= recs.length) {
      showDetails(num-1);
      return;
    }
    if (/apply/i.test(msg)) {
      if (!detail) {
        setMessages((m)=>[...m, {sender:'bot', text:"Pick a role first (1-5), then hit Apply."}]);
      } else {
        onApply();
      }
      return;
    }
    setMessages((m)=>[...m, {sender:'bot', text:"I can show details for a role (1-5) or help you apply."}]);
  };


  return (
    <div className="space-y-3">
      <div className="border rounded p-3 min-h-[320px]">
        {messages.map((m,i)=>(
          <div key={i} className={m.sender==='bot'?'text-left':'text-right'}>
            <div className={m.sender==='bot'?'bg-gray-100 inline-block p-2 rounded':'bg-blue-100 inline-block p-2 rounded'}>
              <span dangerouslySetInnerHTML={{__html: m.text.replace(/\*\*(.+?)\*\*/g,'<b>$1</b>')}} />
            </div>
          </div>
        ))}
        {detail && <div className="mt-3"><JobDetailCard job={detail} onApply={onApply}/></div>}
        <div ref={endRef} />
      </div>
      <form onSubmit={onSend} className="flex gap-2">

      </form>
    </div>
  );

Development Plan: Rejected Candidates Chatbot Portal
Overview and Objectives
We plan to extend the existing TalentMatch (PTX) platform into a Rejected Candidates Portal. This new feature will provide job candidates who were not selected (rejected) with a personalized portal, centered around a chatbot interface. The chatbot will engage the candidate in a conversation, presenting recommended job openings that match their skills or interests. Key objectives include:
                                                                                                                                                                                                                                                                                       * Chatbot-Driven Interface: Introduce a conversational UI as the primary way for rejected candidates to explore opportunities. The chatbot will greet the candidate and guide them to relevant jobs, rather than a static list.

                                                                                                                                                                                                                                                                                       * Skill/Tag-Based Job Recommendations: Leverage the platform’s matching algorithms to suggest open positions similar to the one the candidate applied for. Recommendations will be based on overlapping skills, tags, or job attributes (e.g. same skill set or category)GitHub.

                                                                                                                                                                                                                                                                                       * Seamless Integration via Unique Links: Enable each company (tenant) to generate a unique portal URL to include in rejection emails. This link will embed the specific job ID the candidate applied for, so the portal can automatically load relevant job suggestions for that candidate’s context.

                                                                                                                                                                                                                                                                                       * Candidate Account and Profile Management: Allow candidates to register or log in if they choose to pursue suggested jobs. A candidate can create an account (role "candidate") tied to the company’s tenant to apply for positions, save their data (profile, CV), and manage their applications.

                                                                                                                                                                                                                                                                                       * No External ATS Integration in V1: In this version, we will not integrate deeply with external ATS like Greenhouse beyond using the email link. The system will simply generate a URL (with job identifier) for recruiters to paste into Greenhouse rejection emails. All recommendation logic will occur within PTX using the job ID from the link.

By implementing the above, we aim to improve the candidate experience post-rejection and retain talent in the company’s pipeline, while keeping the solution self-contained within the existing PTX app.
Proposed Solution Overview
1. Chatbot Portal User Experience
The Rejected Candidates Portal will be a dedicated web page in the PTX frontend that can be accessed without logging in (for initial viewing). When a candidate clicks their personalized link in a rejection email, it will open this portal. The key elements on this page:
                                                                                                                                                                                                                                                                                          * Chatbot Interface: A chatbot widget occupies the main area. On page load, the chatbot greets the candidate (e.g. “We're sorry this position wasn't the right fit, but I'd love to help you find other opportunities!”). It will immediately present a few recommended jobs and can answer simple follow-up queries. The candidate can interact via text input.

                                                                                                                                                                                                                                                                                          * Job Suggestions: The chatbot’s first response will include a brief list of recommended job titles (with maybe location or a one-liner) that are similar to the original job. These suggestions are determined by the recommendation engine (see next section). For example, “Based on your interest in a Backend Engineer role, here are 3 other openings that might suit you: 1. Full-Stack Engineer in Tel Aviv, 2. Backend Developer (Remote), 3. Data Engineer in Tel Aviv.”

                                                                                                                                                                                                                                                                                          * Interactive Dialogue: The candidate can click on a suggested job or ask the chatbot for more info. For instance, clicking or typing “Tell me about job #2” will prompt the chatbot to display the full description, required skills, and other details of that job. The chatbot could also handle questions like "Are there roles in Boston?" – filtering or highlighting relevant openings (this could be a stretch goal using keywords or the existing city filter logic).

                                                                                                                                                                                                                                                                                          * Apply and Next Steps: If the candidate indicates interest in a job (e.g., “I want to apply to Full-Stack Engineer”), the chatbot will prompt them to register or log in to proceed. This transition takes them to the account creation/login flow and then to the application process.

This conversational approach makes the experience engaging and personalized, encouraging candidates to continue their job search within the same company’s opportunities.
2. Recommendation Engine (Skill/Tag Similarity)
At the core of the portal is the job recommendation system that finds relevant openings for the rejected candidate. We will build this on existing matching logic in PTX:
                                                                                                                                                                                                                                                                                             * Skills-Based Matching: Each job in the system already stores a set of normalized required skills (skill_set). The platform’s matching service currently computes cosine similarity between skill sets of jobs and candidatesGitHub. We will reuse and adapt this. Essentially, we treat the rejected job’s skill set as a proxy for the candidate’s skills/interest and find other jobs in the same company that have overlapping skills.

                                                                                                                                                                                                                                                                                             * Tags/Categories: In addition to skills, we will consider job tags such as role category or department (e.g. the profession or occupation_field fields in the job data). For example, if the rejected job is in “Data Science” department, jobs with the same tag or department may rank higher. This ensures recommendations aren’t just skill-similar but also contextually relevant (domain or role type).

                                                                                                                                                                                                                                                                                             * Title and Location Overlap: We will incorporate the existing title similarity logic (a 15% weight if job titles share keywords)GitHub. Additionally, if location is important (the current match function can filter by same cityGitHubGitHub), we might decide to prefer jobs in the same city unless remote – possibly as an optional filter. For initial implementation, we can include only jobs that are open within the same tenant (company) and ignore city filtering, to maximize options. Future enhancements can add a toggle for candidates to filter by location if desired.

                                                                                                                                                                                                                                                                                             * Exclusion of Original Job: Naturally, the job the candidate was rejected for will be excluded from recommendations. Also, if that job requisition is closed/filled, it won’t appear anyway if we only consider currently open jobs. We will define “open jobs” by some criteria (e.g. presence in the jobs collection and not marked closed – since our schema doesn’t explicitly have a status, we may assume all listed jobs are open until removed).

                                                                                                                                                                                                                                                                                             * Number of Suggestions: We will fetch a reasonable number (e.g. top 3-5 jobs) to present initially. The matching.get_top_jobs_for_candidate currently returns top k jobs for a candidateGitHub; similarly, we will create a method to get top k jobs similar to a given job. This can use a similar cosine similarity calculation between the rejected job’s skill_set and each other job’s skill_set in the tenant. Weights: ~85% skill overlap, ~15% title/tags overlap, mirroring the platform’s matching strategy for consistencyGitHub.

Technically, implementing this may involve a new backend endpoint, for example: GET /match/recommended_jobs/{job_id}?k=5 (accessible without auth for the portal, see security below). This endpoint will lookup the job’s details, then query the jobs collection for the same tenant and compute similarity scores to return the top results. We will ensure the computation is efficient (the dataset per tenant is typically not huge, and using in-memory calc for a few dozen or hundred jobs is fine; if needed, we can add indices or pre-computed vectors later).
By using the established cosine similarity approach, we ensure recommendations are skill-driven and relevant. Example: If a candidate applied for “Backend Python Engineer” requiring Python and FastAPI, the system might suggest other roles needing Python (e.g. “Full-Stack Python Developer”) or roles in the Engineering department. This keeps candidates engaged with opportunities that fit their profile.
3. Unique Rejection Portal Links
To funnel candidates into this new portal, we will generate a unique link per company that recruiters can paste into their rejection emails. The design for this link mechanism is as follows:
                                                                                                                                                                                                                                                                                                * Link Structure: Likely a URL on our platform like https://<our-domain>/portal?tenant=<tenant_id>&job=<job_id>. This URL encodes the company’s tenant and the specific job ID the candidate applied for. For example: https://talentmatch.company.com/portal?tenant=ABC123&job=JOB-001. In practice, the job parameter might use our internal ID or an external job reference. Note: We might use the platform’s internal job ID (a Mongo ObjectId) in the URL for simplicity, or the external_job_id if that’s easier for recruiters to map from their ATS. Using the internal ID is fine since the link is generated by our system (we will ensure it’s URL-safe).

                                                                                                                                                                                                                                                                                                * Security and Privacy: These links will be publicly accessible (no login required to view the portal), but they only reveal non-sensitive information: a list of open job positions in that tenant. We will enforce that the portal only shows data for the specified tenant. Multi-tenancy isolation remains critical – a candidate from Company A’s link should never see Company B’s jobsGitHub. The tenant parameter in the URL will be used to scope all queries. If an invalid or missing tenant is provided, the portal can show an error or no jobs.

                                                                                                                                                                                                                                                                                                * Configuration UI: In the PTX admin interface (for each tenant), we will add a section to display and manage the rejection portal link. Likely, on the Admin Dashboard or a dedicated “Integration Settings” modal, an admin user can find their company’s portal URL template. For example, it might show a field: “Rejection Portal Link:” https://app.talentmatch.com/portal?tenant=ABC123&job={JOB_ID}. The {JOB_ID} can be documented as a placeholder that the recruiter/ATS should replace with the actual job’s ID when constructing the email link. If using Greenhouse, they can possibly insert a mail-merge token for the job ID. We will provide instructions here.

                                                                                                                                                                                                                                                                                                * Link Generation: We will provide a copy button or similar to easily copy the URL template. Optionally, if we want to be user-friendly, the system might allow generating a full link if the recruiter selects a specific job. However, since rejections are typically templated, providing the template with a placeholder is sufficient.

                                                                                                                                                                                                                                                                                                * No External Integration Needed: This approach avoids direct integration with Greenhouse API. The recruiter just manually adds the link to their email templates in Greenhouse. Therefore, this feature can be implemented entirely within PTX and used immediately by any tenant company without complex setup.

By having a unique tenant-specific link, we ensure each company’s candidates see only that company’s jobs. This also aids tracking (in the future we might log which links get clicked, etc., to gauge candidate engagement).
4. Candidate Registration & Profile Management
While the initial portal view is open to all with the link, applying to a job or saving opportunities will require the candidate to register or log in. We will implement a simple flow to support this:
                                                                                                                                                                                                                                                                                                   * Registration Flow: We will add a "Sign Up" option for candidates, specifically tied to the company’s tenant. This can be a lightweight form asking for name, email, and password (and possibly a checkbox to agree to terms). When a candidate signs up via the portal, the system will create a new user account with role candidate and associate it with the tenant (company) from the URL. In the backend, we will likely expose a new endpoint (e.g. POST /auth/register_candidate) that does not require admin privileges (unlike the current admin-only register) to create a candidate user. This endpoint will:

                                                                                                                                                                                                                                                                                                      * Create a new user in users collection with role "candidate", the provided email/password, name, and tenant_id.

                                                                                                                                                                                                                                                                                                      * Simultaneously, create an entry in the candidates collection with the profile details (full name, email, etc., initially mostly empty except name/email, to be filled out later).

                                                                                                                                                                                                                                                                                                      * Automatically log the user in (issue JWT) or prompt them to log in after registration.

                                                                                                                                                                                                                                                                                                         * Login for Existing Candidates: If a candidate has previously registered (for that tenant’s portal), they can simply log in with their email/password. The portal page will have a “Login” link as well, which takes them to the standard PTX login page (we might enhance the login page to handle candidate role properly, redirecting them to the candidate portal or dashboard after login).

                                                                                                                                                                                                                                                                                                         * Profile Management: Once logged in, a candidate can access a Profile page (the existing CandidateProfilePage in the frontend). We will implement this page to allow candidates to input/update their details: contact info, location, experience, education, and importantly upload their CV. Uploading a CV can be done via a file input; on the backend, we might store the file in MongoDB as binary or (better practice) in an S3 bucket or similar, saving the URL in the candidate profile. Given this is an MVP, storing the file in the database (as a Base64 string or GridFS) could be acceptable, but using cloud storage would be more scalable (we will decide based on time and simplicity). The profile edit form will also allow adding skills (tags) to update their skills field. The backend already supports updating candidate skills and normalizes themGitHub.

                                                                                                                                                                                                                                                                                                         * Job Applications: After logging in, the candidate should be able to express interest or apply to a job from the recommendations. For MVP, since we are not integrating back to Greenhouse in this version, the “Apply” action can be handled in a few ways:

                                                                                                                                                                                                                                                                                                            * Apply via Email Notification: One simple approach is to have an "Apply" button that, when clicked, sends an email notification to the company’s recruiter with the candidate’s profile and the job they’re interested in. The recruiter can then follow up in Greenhouse manually. This could be a stopgap if a full application tracking is too complex now.

                                                                                                                                                                                                                                                                                                            * Internal Application Record: Alternatively, we create an applications collection in our database to log that candidate X applied to job Y, and perhaps provide a basic UI for recruiters to see these applications. However, implementing a full applicant tracking is beyond scope, so a simpler notification system might suffice for now.

                                                                                                                                                                                                                                                                                                            * For the development plan, we propose starting with email notification or a simple stored record for the application, deferring full ATS integration. The focus is giving the candidate a path to express interest easily.

                                                                                                                                                                                                                                                                                                               * Multi-Tenant Candidate Accounts: Each candidate account is tied to a single tenant (the company whose link they used). This means if a candidate uses two different companies’ portals, they would have separate logins (their email might need variation if our system requires unique email per user globally – we will consider using email+tenant composite uniqueness). The current design enforces unique email globallyGitHub, which could be an issue if the same email tries to sign up for another tenant. We may need to relax that to unique per tenant, or allow the same email with different tenants. A quick fix is to adjust the user collection unique index to be on (tenant_id, email) pair instead of just email. We should implement that change as part of multi-tenant best practices so one candidate can register for multiple companies if needed. (This is a schema change that we’ll carefully apply).

                                                                                                                                                                                                                                                                                                               * Privacy & Security: Ensure passwords are hashed (the security utility already handles hashing and verifying passwordsGitHubGitHub). Also, any profile data or CV uploaded by the candidate should be accessible only to authorized users of that tenant (e.g. recruiters of the same company). This aligns with the existing multi-tenancy enforcement in all API routes – we will extend that to any new endpoints as neededGitHub.

By enabling candidate self-service accounts, we not only let them apply to jobs from the chatbot suggestions but also build a talent pool for the company. Over time, recruiters can search these candidate profiles in PTX (the recruiters’ interface could list candidate profiles, which it already partially supports via /candidates endpoints). This turns a rejection into a potential future hire pipeline.

6. Multi-Tenancy and Security Considerations
Because PTX is multi-tenant, we will rigorously maintain isolation and security:
                                                                                                                                                                                                                                                                                                                              * Tenant Isolation: All data queries for jobs or candidates will include a tenant filter. The portal’s public endpoints will require a tenant identifier (from the URL) and use it to query only that tenant’s jobs. The existing system already tags each job and candidate with tenant_idGitHubGitHub. We will use those to ensure one company’s data never leaks to another. Even the new registration flow will attach the correct tenant_id to the new user and candidate profile.

                                                                                                                                                                                                                                                                                                                              * Authentication: The portal page itself is public for viewing suggestions, but any action beyond viewing (like getting detailed data or applying) either requires login or is limited in scope. For example, the job recommendation list and perhaps job detail can be fetched without auth (read-only). However, if one tries to fetch sensitive candidate data or submit anything, they’ll be stopped or asked to log in.

                                                                                                                                                                                                                                                                                                                              * JWT and Roles: We’ll utilize the JWT auth for candidate accounts as already implemented. Upon login or registration, the frontend will store the token and include it in API calls. The backend’s dependency injection (e.g. require_tenant, require_role) will protect private endpoints. We may need to adjust some dependencies for candidate-specific endpoints (for instance, the candidate updating their own profile might depend on a require_role("candidate") or a custom check matching current user).

                                                                                                                                                                                                                                                                                                                              * Data Privacy: The data shown on the portal (job descriptions, requirements) is generally public information that would be on a job listing, so it’s fine to show without login. We will double-check that no confidential fields are returned by our APIs. The existing /jobs/{id} endpoint returns title, description, skills, etc., which are all standardGitHub. That should be safe to expose for the portal as well.

                                                                                                                                                                                                                                                                                                                              * Rate Limiting & Spam: Since the portal endpoint is public, we should consider basic abuse prevention. This could include rate limiting on the recommendation API (to prevent bots from scraping job data across tenants by cycling IDs). Given the scope, a simple approach might be to not expose an index of tenant IDs publicly – one would need a valid link. Tenant IDs (likely Mongo ObjectIds) are not easily guessable. Job IDs included in links are also ObjectIds or external IDs that are not trivial to guess en masse. We deem the risk low for MVP, but it’s noted.

                                                                                                                                                                                                                                                                                                                              * Email/Communication Security: If implementing email notifications for applications, ensure not to expose candidate email to others via CC. Likely, we’d send an email directly to the company’s HR inbox. We will use secure mail transfer and perhaps an email template that includes candidate info, to streamline recruiter’s work.

By following these practices, we maintain the best-practice security and isolation as expected in a multi-tenant SaaSGitHub, providing each company and candidate a safe experience.

                                                                                                                                                                                                                                                                                                                                          * Return these jobs with basic info: job_id, title, location, maybe a snippet of description or the overlapping skills for transparency.
